# Release binaries

Download otgo from the [GitHub releases](https://github.com/darron/go-opentunnel/releases).
Stable releases include CLI archives for macOS (`darwin`) and Linux, each for
`amd64` and `arm64`. Apple silicon uses `darwin_arm64`; Intel Macs use
`darwin_amd64`. Each archive contains only `otgo` and the MIT license.

Windows builds are not published: protected profile storage is not supported
there. The Go library remains available through Go modules.

## Verify and install

Download the archive for your machine and its matching `.sha256` file. For
example, on Apple silicon:

```sh
gh release download v0.16.2 --repo darron/go-opentunnel \
  --pattern 'otgo_0.16.1_darwin_arm64.tar.gz*'
shasum -a 256 --check otgo_0.16.1_darwin_arm64.tar.gz.sha256
tar -xzf otgo_0.16.1_darwin_arm64.tar.gz
./otgo version
install -m 755 otgo /usr/local/bin/otgo
```

Choose a writable directory on your `PATH` for installation. On Linux, use
`sha256sum --check` instead of `shasum -a 256 --check`. `SHA256SUMS` contains all
four archive hashes; individual checksum files let you verify one download.
Checksums detect changed bytes; they are not independent signatures.

The binaries require no Go installation. They report the release version, full
source commit SHA and `clean`. [Homebrew](HOMEBREW.md) installs the same compiled
executable from these archives; it does not rebuild the source.

## Publish a release

1. Update `Version` in `types.go` and add a dated changelog entry. Run the repo
   checks, commit and push to `main`, and check CI on the release commit.
2. Create and push an annotated `vMAJOR.MINOR.PATCH` tag for that commit.
3. Publish the GitHub release with its release notes. Keep release notes on the
   release; do not add a release-note file to `docs/`.
4. Check **Publish release binaries**, including its final Homebrew dispatch,
   then the tap's **Update otgo** workflow. Asset publication must succeed before
   the tap starts. A tag push alone does not start either path. Finish the
   publication verification record after the jobs pass.

The binary workflow resolves the tag to an immutable commit, verifies that the
source version matches, and builds only `./cmd/otgo` with the pinned Go 1.27.3 toolchain and
`CGO_ENABLED=0`. It embeds the verified revision explicitly. It checks native
Linux and macOS execution before a fresh runner uploads the archives, individual
checksums and `SHA256SUMS`. The upload job has `contents: write`; build and smoke
jobs have read-only repository access. Asset publication needs no additional
secret; the final Homebrew dispatch uses `HOMEBREW_TAP_TOKEN`.

Drafts and prereleases are skipped. If a workflow creates the release using
`GITHUB_TOKEN`, explicitly dispatch `release-binaries.yml` with
`update_homebrew=true`: GitHub suppresses most further events generated by that
token. The
[Homebrew guide](HOMEBREW.md#automation) explains that trigger rule and the tap
credential.

## Retry or backfill assets

Run from `main` for an already-published stable release:

```sh
gh workflow run release-binaries.yml --repo darron/go-opentunnel \
  --ref main -f tag=v0.16.2
```

The workflow uses its own automation revision but builds the requested release's
source. It does not move the tag or change release notes. Manual runs do not
dispatch Homebrew unless `-f update_homebrew=true` is supplied; use that option
only when updating the current stable formula, not for historical backfills.
Retries skip byte-identical assets and upload missing files. Different existing
bytes cause failure; the workflow never replaces them. A changed Go toolchain
can produce different binaries on a later rebuild, so inspect that failure and
publish a new version when needed.

Local packaging and checksum checks:

```sh
python3 -m unittest discover -s scripts -p 'test_*.py'
actionlint
```
